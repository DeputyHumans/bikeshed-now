A link shortener

Design review · draft for comment

We want short, stable, shareable links that resolve fast and cannot be guessed. This document proposes the smallest system that does that, and is explicit about the five decisions it has not made.

Nothing here is novel. The interesting parts of a link shortener are not the shortening — they are what happens at the tail: what an identifier reveals, what happens when one is deleted, and what the redirect costs at the ninety-ninth percentile.

The problem

Links we share today are long, they encode structure that changes, and they break when the structure does. Three concrete failures, all of them real:

  • A link pasted into a document last quarter now resolves to a 404, because the path it encoded was reorganized.
  • A link read aloud in a meeting cannot be typed by anybody hearing it.
  • A link forwarded outside the company discloses an internal hostname and a directory layout, neither of which we meant to publish.

The third is the one that makes this worth building rather than tolerating.

Goals and non-goals

Goals

  • A link of at most twenty characters, typable and readable aloud.
  • Stable: once created, it resolves to the same target for as long as it exists, or it stops existing. It never silently points somewhere else.
  • Fast: the redirect is served from cache in the common case.
  • Revocable: the person who created a link can withdraw it.

Non-goals

  • Analytics. Counting clicks means recording who clicked, and that is a different product with a different set of obligations.
  • Custom domains. One host. Two is an operational surface, not a feature.
  • Editable targets. Repointing a live link is how a link somebody trusted becomes a link to something else.

Shape of the system

Three pieces, and deliberately no more.

PieceDoesDoes not
Creator Takes a target URL and an optional expiry. Returns an identifier. Validate that the target exists. That is a race we would lose.
Store Maps identifier to target, with a creation time and an owner. Keep history. A link has one target, forever or not at all.
Redirector Reads the map and issues a redirect. Log the request. See non-goals.

Choosing an identifier

The identifier is the whole design compressed into one decision, because it determines both the length of a link and what somebody can learn by trying other links.

Sequential

Shortest possible, and enumerable. Anybody with one link can walk the whole corpus by incrementing. That is disqualifying for a system whose whole justification is that links currently leak too much.

Hash of the target

Deduplicates for free: the same target always shortens to the same link. It also means an identifier is a guessable function of the target, so anybody who can guess a URL can confirm somebody shortened it.

Random

Eight characters from a 32-symbol alphabet is forty bits — a trillion possibilities, so guessing is not a strategy — and it reveals nothing about the target or about when the link was made. The alphabet excludes 0, 1, i and l, which are the characters people mistype when reading a link aloud.

Proposed: random, eight characters, Crockford base32.

Storage

A single table, keyed by identifier: 

id        text primary key
target    text not null
owner     text not null
createdAt timestamptz not null
expiresAt timestamptz

There is no updatedAt, because there is no update. A link is created and eventually deleted; it is never repointed. That single constraint removes the entire class of "the link I shared now goes somewhere else" problems, and it is why the table has no history.

Expiry is a column rather than a job. The redirector checks it on read, and a periodic sweep reclaims rows. Deleting on a schedule alone would leave a window where an expired link still resolves.

The redirect path

This is the only path that has to be fast, and it is four steps:

  1. Look the identifier up in an in-process cache.
  2. On a miss, read the row.
  3. If it is missing or expired, return 404. Not 410: distinguishing "never existed" from "existed and is gone" tells a prober which identifiers were real.
  4. Otherwise issue a 302.

Why 302 and not 301. A permanent redirect is cached by the browser indefinitely, which means revocation does not work: somebody who followed a link once keeps following it after it is withdrawn. A temporary redirect with a short cache lifetime gives us revocation in seconds at the cost of a little more traffic.

Abuse

A shortener is a laundering tool: it takes a URL somebody would not click and makes it look like ours. Three mitigations, in the order they are worth doing:

  1. Attribution. Every link records who made it. Most abuse stops being interesting once it is not anonymous.
  2. An interstitial for off-domain targets. Showing where a link goes before following it removes the disguise, which is the only thing the attacker wanted.
  3. A denylist. Last, because it is the one that needs maintaining forever and catches the least.

Open questions

Five statements that are contestable. Each is written as a claim rather than a question, so disagreeing with one is a matter of highlighting it and saying why.

1. Eight characters is the right length. Six would be shorter and still gives a billion possibilities, which is plenty against a rate-limited prober.

2. Links should never expire by default. A link that quietly stops working is worse than a long one, and defaults decide almost everything.

3. The interstitial should be shown for every off-domain target, with no way to skip it. A remembered "do not show this again" is a setting an attacker can rely on.

4. Not counting clicks is worth the complaints. Somebody will ask for it within a month, and the answer has to be the same answer in a year.

5. Deleting a link should free its identifier for reuse. The alternative leaks the total number ever created, which is a business fact, not a technical one.

Plan

  1. The table, the creator and the redirector. No cache, no interstitial.
  2. The interstitial, because it is the mitigation that matters most.
  3. The cache, once there is enough traffic to measure the difference.
  4. The expiry sweep.

Steps one and two are a week. Three and four are worth doing only after somebody has complained about latency or storage, and not before.
