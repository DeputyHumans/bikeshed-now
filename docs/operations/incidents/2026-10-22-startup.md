# 2026-10-22: shared function startup failure

## Impact and evidence

The landing page remained available while many backend operations failed. Cloud
Run reported that containers did not listen on the configured port before the
startup deadline. The redeploy failed across all 33 functions despite successful
builds. Older revisions also failed to start, so a traffic rollback alone was
not a reliable recovery path.

The first observed failure was at 21:21 UTC, before the 21:50 redeploy. Comparing
229 source files found identical application contents. A shared managed-runtime
or startup problem is the leading hypothesis; the exact provider-side cause is
**unconfirmed**. A provider incident viewed during investigation was not proven
to be causally related.

Recovery was first observed at 22:38 UTC, before the operator changed runtime
update policy. Do not attribute that initial recovery to the policy change.
After a small recovery probe and rebuilding the fleet, all latest revisions
were ready, production deployment completed, and public and authenticated
private-document checks passed. A fifteen-minute observation found no new
startup/server errors; the user confirmed normal private-document rendering.

Detailed bindings, source manifests, operation IDs and logs are retained in
private incident evidence, outside this repository.

## Why detection was late

There were no configured uptime checks, alert policies or notification channels.
The static landing page was an inadequate health signal. A build succeeding did
not prove that the deployed runtime could start, access dependencies or serve
requests. The failed workflow history also remained visible after services had
recovered, making historical deployment status easy to confuse with live health.

## Follow-up

- Probe landing, hosted dependencies and the direct backend separately.
- Email on unready revisions, backend errors, stuck events, failed deployments,
  provider incidents and monitoring drift; detect a missing hourly audit.
- Apply runtime updates on deployment, check the policy after every release,
  and remind an operator about actual builds older than fourteen days.
- Retain source-file hashes and revision/build evidence for thirty days.
- Keep recovery manual and verify a private document plus fifteen clean minutes
  before closing an incident. See the [runbook](../monitoring.md).

These measures reduce detection time and unexpected runtime changes. They do
not establish the provider root cause or guarantee that a provider outage cannot
recur. Public dependency probes do not replace authenticated user-flow testing.
